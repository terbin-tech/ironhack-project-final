# Security

This file describes how the AWS deployment of Expensy handles credentials, secrets, roles and network access, where its data lives and how long it is kept, and which gaps are known. The setup itself is in the [README](README.md).

## Authentication

| Who | How they authenticate |
|---|---|
| GitHub Actions | GitHub's OIDC token, exchanged for a short role session ([GitHub OIDC in AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)); no AWS key is stored in GitHub |
| Pods (backend, the DocumentDB user Job, ExternalDNS, the CloudWatch agent) | [EKS Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html): short-lived credentials per service account |
| Argo CD | The EKS Argo CD capability's own IAM role. People sign in to its UI through IAM Identity Center, as a user with no AWS permissions. |
| The operator running Terraform and `kubectl` | An IAM user's access key on the operator's machine (see [Known gaps](#known-gaps)). Whoever applies `infra/main` becomes cluster admin through an EKS access entry. |

The pipeline never connects to the cluster and holds no kubeconfig: it records image tags in Git, and Argo CD applies them from inside the cluster.

## IAM roles

Every Pod Identity role trusts only its own namespace, service account and cluster, and only when EKS makes the request for this AWS organization (condition `aws:SourceOrgId`).

| Role | May do |
|---|---|
| `martin-project-final-backend` | Read two secrets: the backend's DocumentDB user (`martin-project-final-docdb-expensy`) and its Valkey user (`martin-project-final-valkey-expensy`). It cannot read the DocumentDB master secret (`aws iam simulate-principal-policy`: `implicitDeny`). |
| `martin-project-final-docdb-user` | Read the DocumentDB master secret and the backend's DocumentDB secret, for the Job that creates the backend's database user |
| `martin-project-final-github-build` | Push images to the two ECR repositories (`martin-expensy-frontend`, `martin-expensy-backend`) and get an ECR sign-in token; trusted only for the `main` branch of this repository |
| `martin-project-final-github-record` | Only `ecr:DescribeImages` on the two repositories; trusted only for jobs in the `production` environment, which needs a reviewer's approval |
| `martin-project-final-external-dns` | Change only `martin.diogo.world` and its two TXT ownership records in the one hosted zone |
| `martin-project-final-cloudwatch` | The AWS managed policy `CloudWatchAgentServerPolicy`, which the add-on recommends. It allows writing logs and metrics anywhere in the account, more than this cluster needs; it stays because it is AWS's documented policy. |
| `martin-project-final-argocd` | The Argo CD capability's role. Inside the cluster Argo CD has cluster admin, limited by its project to this repository, the pinned chart sources and a list of namespaces. |

The GitHub roles trust GitHub's immutable OIDC subject, which carries the owner's and the repository's numeric IDs, so a repository recreated under the same name cannot assume them.

## Secrets

| Secret | Where it comes from | Who reads it |
|---|---|---|
| DocumentDB master password | Generated by AWS and kept in Secrets Manager (`manage_master_user_password`), rotated every seven days ([DocumentDB and Secrets Manager](https://docs.aws.amazon.com/documentdb/latest/developerguide/docdb-secrets-manager.html)) | Only the DocumentDB user Job, fresh on each run |
| The backend's DocumentDB password | Generated by Terraform with an ephemeral resource and written to Secrets Manager with write-only arguments (Terraform features that never store the value), so it is in neither the state nor a plan | The backend, as a mounted file |
| The backend's Valkey password | The same way | The backend, as a mounted file |
| Grafana's admin password | A Kubernetes Secret created once by hand with a random value, never in Git | Grafana |
| The two GitHub repository secrets | The role ARNs, stored as secrets so that GitHub masks them in logs; they grant nothing without GitHub's OIDC token | The deploy workflow |

The AWS Secrets and Configuration Provider (ASCP) mounts each secret as files in the pod that needs it ([ASCP with Pod Identity](https://docs.aws.amazon.com/secretsmanager/latest/userguide/ascp-pod-identity-integration.html)), and no Kubernetes Secret is synced from them, so no app password is stored in the cluster. The backend's DocumentDB user has the built-in role `readWrite` on the database `expensy` only ([DocumentDB role-based access control](https://docs.aws.amazon.com/documentdb/latest/developerguide/role_based_access_control.html)). The other Kubernetes Secrets in the cluster are cert-manager's ACME account keys, the site's TLS certificate and certificates the platform components make for themselves.

The repository holds no secret: `expensy_backend/.env` holds only the brief's local demo values for Docker Compose. The account ID and the Route 53 zone ID are kept out of the public repository and its workflow logs: Terraform reads them from AWS, and `configure-aws-credentials` masks the account ID. GitHub secret scanning and push protection are on for this repository ([secret scanning](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning), [push protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)).

## Network

- The Kubernetes API's public endpoint accepts only the addresses in the git-ignored `infra/main/terraform.tfvars`; the private endpoint is on.
- DocumentDB (27017) and Valkey (6379) sit in private subnets and accept connections only from the cluster's security group.
- TLS: the browser reaches the gateway over HTTPS with a Let's Encrypt certificate, and HTTP redirects to HTTPS. The backend reaches DocumentDB over TLS, verified against the RDS CA bundle, and Valkey over TLS, verified against Node's built-in list of certificate authorities. Inside the cluster, the gateway reaches the pods over plain HTTP.
- Network policies: every namespace whose pods use the pod network has a default deny with explicit allows, and a cluster-wide baseline policy denies the traffic of any pod that no namespace policy selects ([EKS Auto Mode network policies](https://docs.aws.amazon.com/eks/latest/userguide/auto-net-pol.html)). Pods on the host network are not covered: node-exporter, the CloudWatch agent, Fluent Bit and the GuardDuty agent.
- In `expensy` the gateway may reach the frontend on 3000 and the backend on 8706, Prometheus may reach the backend on 8706, the backend may reach the private subnets on 27017 and 6379, the DocumentDB user Job on 27017, and every pod may use DNS. A test pod in `expensy` and one in `default` could not reach the internet.
- Valkey has role-based access control on, and its default user cannot connect. The backend's user may run only `GET`, `SET` and `DEL` on the key `expenses`, plus `INFO` and `CLIENT`, which its client sends while connecting.

## Workloads

- Pod Security: `expensy`, `gateway`, `nginx-gateway`, `cert-manager`, `external-dns`, `argocd` and `default` enforce [`restricted`](https://kubernetes.io/docs/concepts/security/pod-security-standards/). `monitoring`, `amazon-cloudwatch`, `aws-secrets-manager` and `amazon-guardduty` are `privileged`, because node-exporter, the CloudWatch agent, Fluent Bit, the Secrets Store CSI driver and the GuardDuty agent need host access.
- The containers in `expensy` run as non-root (uid 1000, the Job uid 999) with all capabilities dropped, no privilege escalation, a read-only root filesystem, no Kubernetes API token mounted, CPU and memory requests and limits, and readiness and liveness probes.
- Grafana has a Role in its own namespace instead of the chart's default ClusterRole, so it can read ConfigMaps and Secrets in `monitoring`, which its sidecars watch for dashboards and data sources, and in no other namespace. kube-state-metrics does not collect Secrets.

## Supply chain

- Images are tagged with the commit SHA, the ECR tags are immutable, and the pods run them by digest (`tag@sha256:...`), which the pipeline records in Git.
- The base images and the cert-manager images are pinned by digest. Every GitHub Action is pinned to a full commit SHA, and the repository setting that requires such pins is on.
- The dependencies are on releases without known advisories where one exists (`npm audit`): express 4.22, mongoose 8.24, Next.js 15.5, axios 1.21, sharp 0.35.
- `.github/dependabot.yml` asks for weekly updates of the actions, the npm packages and the Docker base images.
- The Terraform state bucket refuses requests without TLS, logs access to a separate bucket and keeps every version, and an alarm fires on any request to it without TLS.

## Data protection and compliance

This is a course project with no real personal data: only the expenses typed in during the demo, each a name, an amount and a category. The app has no user accounts and no authentication, so everything stored is visible to anyone who opens the site.

### Where the data lives

Everything runs in one AWS account in us-east-1 (N. Virginia, United States).

| Data | Where | Encrypted at rest |
|---|---|---|
| Expenses | Amazon DocumentDB, private subnets | Yes, `storage_encrypted` (AWS managed key) |
| Cache of the expense list (5 minutes) | ElastiCache for Valkey, private subnets | Yes, at-rest encryption on |
| Passwords | AWS Secrets Manager | Yes, AWS managed key `aws/secretsmanager` |
| Container, control plane and VPC flow logs | CloudWatch Logs | Yes, CloudWatch Logs always encrypts log data |
| Metrics | Prometheus, on a node's disk, no persistent volume | Yes, the nodes' EBS volumes are encrypted with KMS |
| Kubernetes objects | EKS control plane (etcd) | Yes, EKS envelope-encrypts all Kubernetes API data with an AWS owned key ([EKS default envelope encryption](https://docs.aws.amazon.com/eks/latest/userguide/envelope-encryption.html)) |
| Terraform state, S3 access logs, CloudTrail files | Two S3 buckets in the account regional namespace | Yes, S3 default encryption; TLS required for every request |
| Container images | Amazon ECR | Yes, ECR default encryption |

In transit, see [Network](#network).

### Retention

| Data | Kept | Set in |
|---|---|---|
| Container Insights log groups (`/aws/containerinsights/martin-project-final/...`: application, dataplane, host, performance) | 7 days | `infra/main/logs.tf` |
| EKS control plane logs | 7 days | `infra/main/cluster.tf` |
| VPC flow logs of rejected packets, and the state bucket's CloudTrail log group | 7 days | `infra/main/network.tf`, `infra/bootstrap/alarm.tf` |
| Prometheus metrics | 10 days at most, and only while the Prometheus pod lives | `monitoring/values.yaml` |
| DocumentDB automated backups | 7 days | `infra/main/docdb.tf` |
| Valkey snapshots | 7 days | `infra/main/data.tf` |
| S3 access logs, CloudTrail files, old versions of the Terraform state | Until teardown (no lifecycle rule) | `infra/bootstrap/main.tf` |
| Expenses | Until teardown; the app has no delete function | |

The teardown in the README deletes all of it, with no final snapshot. Secrets Manager keeps deleted secrets for its recovery window before removing them.

### Personal data

The app asks for no personal data: there are no accounts and no email addresses. It can still hold personal data in two places: whatever someone types into an expense's name, and the source addresses of rejected packets in the VPC flow logs, which can be public IP addresses and are kept 7 days. The backend logs no request bodies and, for errors, only the error's name and message. The gateway's logs show the load balancer's addresses, not the visitors'.

### GDPR

GDPR would apply if the site served people in the EU, or if its operator were established in the EU (Article 3). For that, this deployment would need more than it has:

- The data is in a US region. Storing EU users' data there is a transfer to a third country, which needs a basis such as the EU-US Data Privacy Framework or standard contractual clauses; this project has not assessed that. An EU region (for example eu-central-1) would avoid the transfer.
- Without accounts, one person's data cannot be told apart from another's, so an access or deletion request for one person cannot be answered.
- There is no privacy notice.

In line with GDPR's principles already: encryption at rest and in transit, short log retention, least-privilege access to the data, and an app that asks for no personal data.

No health or payment card data is stored, so HIPAA and PCI DSS do not apply, and no other framework is claimed.

### Checklist

| Item | State |
|---|---|
| Data region known and documented | Yes, us-east-1 |
| Encryption at rest for every store | Yes ([table](#where-the-data-lives)) |
| Encryption in transit outside the cluster | Yes ([Network](#network)) |
| Secrets outside Git, logs and Terraform state | Yes ([Secrets](#secrets)) |
| Retention set for logs and metrics | Yes: CloudWatch logs 7 days, metrics 10 days; S3 access logs and CloudTrail files until teardown |

## Known gaps

- The operator signs in with a long-lived IAM user access key. A short-lived session through IAM Identity Center, which already serves Argo CD, would be better.
- The AWS account is shared with the course: teachers and students have administrator access, so nothing stored in it is hidden from them.
- The DocumentDB app password and the Valkey password are not rotated. The backend reads them once at start, so a rotation would need a restart, and no rotation function is deployed.
- The DocumentDB user Job runs on every sync of the `expensy` Application, with the master credentials, to create or update the backend's user. It prints only the user's roles.
- The site has no authentication, and the backend's CORS policy allows any origin.
- Inside the cluster, the gateway reaches the pods over plain HTTP; there is no service mesh.
- Argo CD has cluster admin. Its project limits the sources and the destination namespaces but allows every cluster-scoped kind.
- cert-manager, its cainjector, NGINX Gateway Fabric and the Prometheus operator can read Secrets in every namespace, as their charts set them up.
- A new pod is not covered by its network policies in its first seconds: a request made the moment a test pod started went through, and the same request 20 seconds later was blocked.
- `CloudWatchAgentServerPolicy` is broader than needed (see [IAM roles](#iam-roles)).
- The images are not scanned. The account's registry uses Amazon Inspector enhanced scanning, which replaces the repositories' scan on push, and Inspector has no coverage for these two repositories.
- Dependabot may not find the Dockerfiles, since they are named `Dockerfile.backend` and `Dockerfile.frontend`, not `Dockerfile`.
- DocumentDB's audit log is off, so database sign-ins and user changes are not logged.
- The `main` branch rule blocks force pushes and deletion but requires no pull request or passing checks.
- One advisory remains in the frontend's build tooling: the PostCSS copy bundled inside Next.js 15.5 (source map reads at build time), fixed only in Next.js 16. It does not run in the served app.
- The frontend sends a fixed placeholder `Authorization` header (`expensy_frontend/api/apiclient.tsx`, from the original app), which the backend ignores.
